# Temp0.7 디스코드 봇 작업 계획

- 기준 문서: [PRD.md](./PRD.md)
- 작성일: 2026-09-09
- 계획 작성 시 초기 상태: PRD만 존재하며 애플리케이션 코드·테스트·배포 설정은 없었음.
- 목표: 회의 운영 자동화를 먼저 완성하고, 뉴스 큐레이션과 회의록 RAG를 순차적으로 추가한다.
- 이 문서의 기술 구성과 미정 정책은 구현을 위한 제안이며, PRD의 확정 요구사항과 구분한다.

## 현재 착수 범위 (사용자 요청 반영)

봇 토큰 하나를 여러 서버(동아리 서버, 테스트 서버 등)에서 공유하고, 서버·공지 채널 설정은 환경변수가 아니라 DB로 옮겼다. `/공지채널추가`·`/공지채널제거`·`/공지채널목록`으로 서버마다 하나 이상의 공지 채널을 등록·관리하며, 모든 명령은 그 명령을 입력한 서버의 일정·채널만 조회·변경한다. 스케줄러는 20초마다 등록된 모든 서버의 일정을 확인하고, 발송 이력은 서버·채널 조합으로 기록해 한 채널의 전송 실패가 같은 서버의 다른 채널이나 다른 서버에 영향을 주지 않는다. 새 서버를 운영에 추가할 때는 코드나 `.env` 변경 없이 봇을 초대하고 슬래시 명령으로 등록하기만 하면 된다. 수동 공지와 오전 9시·회의 10분 전 자동 공지에는 모두 `@everyone`을 사용한다. 테스트 연결 메시지는 멘션 없이 보낸다. 자세한 설치·명령·정책은 README를 따른다.

첫 구현 범위를 **회의 알림만**으로 축소한다. FR-4·FR-5·FR-6에 해당하는 회의 설정, 당일 09:00 알림, 10분 전 전체 알림과 운영용 조회·해제·연결 테스트를 구현한다. 발표자 관리·멘션과 DM, 뉴스, RAG는 이후 범위로 보류한다. 최초 코드와 로컬 테스트가 추가되었으며 Discord 실서버 검증에는 사용자 환경 설정이 필요하다. 설치 방법과 실제 동작 정책은 [README.md](../README.md)를 따른다. 아래 단계들은 전체 PRD를 위한 후속 로드맵으로 유지한다.

## 1. 구현 전 정리할 정책

| 항목 | PRD의 모호함 또는 충돌 | 제안하는 기본값 |
|---|---|---|
| 시간대 | 09:00의 시간대가 없음 | 모든 사용자 일정은 Asia/Seoul, 저장 시각은 UTC |
| 뉴스 수집 | Flow는 09:00 수집 시작, FR-1은 09:00 이전 수집 완료 | 08:30 수집 시작, 08:55 마감, 09:00 준비된 결과 발송. 소스별 시간 제한 적용 |
| 뉴스 선별 개수 | N이 전체 기준인지 분반별인지 불명확 | 분반별 N개, 초기 N=3. 같은 기사는 한 번 표시하고 관련 분반 태그 부여 |
| 발표자 적용 범위 | ‘이번 주’와 회의 다음날 다음 발표자 요청이 충돌할 수 있음 | `/발표자설정`은 다음 예정 회의에 연결하고 확인 메시지에 회의 날짜 표시 |
| 회의 변경 | 이미 설정한 발표자 처리 규칙이 없음 | 동일 회차의 시간 변경에는 발표자를 유지하고 과거 회차 기록은 보존 |
| 회의 다음날 DM | 실제 회의 개최 여부를 알 수단이 없음 | 예정 시각이 지난 회차를 기준으로 다음날 09:00 요청. 실제 개최·취소 판별은 추가 요구사항 |
| 이른 회의 | 09:00 이전 회의에는 당일 알림이 회의 후 도착 | 권장: 당일 09:00 알림은 생략, 10분 전 알림은 유지. PRD 수용 기준의 예외로 확정 필요 |
| 재시작 후 누락 알림 | 과거 알림을 재발송할지 미정 | 이미 지난 회의의 10분 전 알림은 생략. 뉴스·당일 알림·DM의 보충 발송 허용 시간은 설정으로 정의 |
| RAG 접근 범위 | 회의록 열람 권한과 질문 권한의 관계가 없음 | 지정 회의록 채널을 열람할 수 있는 사용자만 질문 가능, 답변은 질문자에게만 표시 |
| RAG 10초 제한 | 모델/API 지연 시 동작이 없음 | 초기 처리 응답을 먼저 보내고, 최종 답변도 요청부터 10초 이내 목표. 초과 시 시간 초과 안내 및 실패 지표 기록 |

시간 초과 안내는 FR-12의 정상 답변 성공으로 계산하지 않는다. 오전 회의 예외 등 원문과 다른 정책은 구현 착수 시 확정하고 PRD에 반영한다.

## 2. 제안 구조

8명 규모의 단일 디스코드 서버를 초기 대상으로, Python 기반 단일 봇 프로세스와 영속 저장소로 시작한다. Cog 요구사항에 맞춰 기능을 분리하고, 실제 패키지·버전은 구현 시 공식 문서와 호환성을 확인해 고정한다.

- `cogs/`: 뉴스, 회의, 발표자, 질문 명령 및 이벤트 연결.
- `services/`: 일정 계산, 뉴스 선별, 문서 수집·검색·답변 등 업무 로직.
- `repositories/`: SQLite 기반 설정, 회의 회차, 발표자, 작업 실행 이력, 수집 체크포인트 저장.
- `integrations/`: Discord, RSS/API, 문서 추출, 임베딩·답변 모델, 벡터 저장소 어댑터.
- `scheduler/`: 저장된 일정에서 실행할 작업을 계산하고 재시작 시 복원.
- `tests/`: 핵심 업무 규칙과 외부 연동 실패 상황 검증.

벡터 저장소는 우선 로컬 영속형 구성을 검토하되, 조회 권한 필터·청크 삭제·재시작 후 데이터 유지가 가능한지 작은 검증으로 결정한다. 임베딩·답변 모델은 한국어 품질, 비용, 10초 응답 목표를 확인해 선정한다.

주요 데이터는 서버 설정, 회의 시리즈·회차, 회차별 발표자, 발송 이력, 뉴스 원문·선별 결과, 원본 문서·청크, 채널별 수집 체크포인트다. 회의 시리즈와 개별 회차를 구분해 주차 경계와 일정 변경을 처리한다.

## 3. 단계별 작업

### 단계 1 — 공통 기반

작업:
- 프로젝트 구조, 의존성 고정, 실행 진입점, 환경변수 예제 작성.
- 봇 토큰, 서버·채널 ID, 팀장 ID, 관리자 역할, 시간대 등 설정 검증.
- Cog 로딩, 명령 등록, 공통 오류 응답, 구조화 로그 구현.
- DB 초기화·마이그레이션과 영속 저장소 구성.
- 작업 실행 이력과 중복 실행 방지 키 설계: 서버 + 작업 종류 + 회차/발송일.
- 재연결 시 스케줄러가 중복 실행되지 않도록 수명주기 관리.

완료 기준: 테스트 서버에서 봇이 연결되고, 재시작 후 설정이 유지되며, 잘못된 설정은 명확한 오류로 표시된다.

### 단계 2 — 회의·발표자 관리 전체 흐름

대상: FR-4~FR-9. P0 기능과 바로 연결된 P1 알림을 함께 완성한다.

작업:
- `/회의설정`: 관리자 권한 확인, 요일·시간 검증, 저장 및 알림 재등록.
- `/발표자설정`: 팀장 ID 확인, 서로 다른 서버 구성원 3명 검증, 대상 회차에 저장·덮어쓰기.
- 당일 09:00 알림과 10분 전 알림 구현. 10분 전 메시지에 `@everyone`, 발표자 3명 또는 ‘발표자 미설정’, 남은 시간 표시.
- 회의 다음날 09:00 팀장 DM 구현 및 차단 실패 로그 기록.
- 명시적 멘션 허용 설정과 봇의 채널·전체 멘션 권한 확인.
- 시간 변경 시 이전 예약 무효화, 실행 직전 최신 회차 상태 재확인.

완료 기준: 권한 거부, 발표자 미설정, 덮어쓰기, 자정·주차 경계, 일정 변경, DM 차단, 재시작 시나리오를 검증한다. 테스트 서버에서는 압축한 일정으로 전체 알림 흐름을 확인한다.

### 단계 3 — 뉴스 큐레이션

대상: FR-1~FR-3. 실제 뉴스 수신까지 확인하도록 P1인 채널 전송을 함께 구현한다. 상세 설계는 [NEWSLETTER_DESIGN.md](./NEWSLETTER_DESIGN.md) 참고. 서버별 뉴스레터 채널 등록(`/뉴스레터채널추가` 등)은 이미 구현되어 있으며, 이 단계는 그 채널 목록을 소비하는 수집·큐레이션·발송 로직을 다룬다.

작업:
- 소스 목록, 논문 소스 제외 규칙, 분반별 키워드·가중치, N을 설정화.
- RSS 우선 수집 구조를 만들고 필요한 API 소스를 어댑터로 추가.
- 소스별 제한 시간·재시도·실패 로그와 독립적인 실패 처리 구현.
- 게시 시각·수집 체크포인트로 신규 글 판정, URL 정규화와 기사 ID로 중복 방지.
- 키워드 기반 점수와 동점 정렬 기준 구현. 초기에는 운영자가 선정 결과를 보고 가중치를 조정할 수 있도록 점수 기록.
- 제목·출처·링크·분반을 포함한 임베드 생성, 메시지 크기에 따라 분할 전송.
- 수집 결과가 없거나 일부 소스만 성공한 날, 발송 일부 실패 후 재시도 정책 구현.

완료 기준: 샘플 피드로 관련도·중복·논문 제외를 확인하고, 한 소스가 실패해도 나머지 결과가 정해진 채널에 전송된다.

### 단계 4 — 회의록 수집·인덱싱

대상: FR-10~FR-11.

작업:
- 지정 채널의 이력 조회·메시지 내용·첨부 접근에 필요한 권한과 설정 확인.
- 페이지 단위 백필과 중단 후 재개 구현. 실시간 수집과 겹치는 메시지는 같은 식별자로 병합.
- 메시지 ID 기반 체크포인트와 처리 상태를 저장하고, 실패한 항목은 별도 재시도 대상으로 유지.
- docx 문단·표 추출, 크기 제한과 손상 파일 처리 구현.
- 메시지 ID·첨부 ID·내용 해시 기반 원본 식별 및 청킹·임베딩 구현.
- 채널명·작성자·작성일·원본 링크와 권한 필터용 서버·채널 ID 저장.
- 인덱싱 성공 후 처리 완료 기록. 메시지 수정·삭제에 따른 청크 교체·삭제는 운영 보완 범위로 포함.

완료 기준: 백필 중 재시작해도 누락 없이 재개하고 중복 청크가 생기지 않는다. 문단·표 샘플과 손상 파일을 검증하며, 수집 작업이 명령 응답을 막지 않는다.

### 단계 5 — RAG 질문·답변

대상: FR-12.

작업:
- `/질문` 권한 검사와 초기 처리 응답 구현.
- 허용된 원본만 검색하도록 필터링하고, 검색 결과 수·관련도 기준·문맥 길이를 설정화.
- 검색된 내용에 근거한 한국어 답변과 원본 메시지 링크 생성.
- 근거가 부족하면 ‘찾을 수 없음’을 반환하고, 존재하지 않는 출처가 출력되지 않도록 검증.
- 문서 안의 명령형 텍스트를 지시가 아닌 검색 자료로 취급하도록 답변 흐름 구성.
- 검색·모델 호출의 제한 시간, 동시 요청 수, 실패 안내와 지연 시간 기록 구현.

완료 기준: 일반 질의, 표 안의 정보, 근거 없는 질문, 접근 권한이 없는 질문을 포함한 평가 세트로 검증한다. 정상·동시 요청 시 최종 답변의 10초 초과 건수를 기록하고, 목표를 충족하지 못하면 모델·검색 범위를 조정한다.

### 단계 6 — 배포·운영 검증

작업:
- 상시 실행 환경과 재시작 정책, 비밀값 주입, 영속 볼륨 구성.
- DB·벡터 데이터 백업 및 복원 절차 작성.
- 토큰이나 회의록 원문을 불필요하게 로그에 남기지 않도록 확인.
- 실행법, 명령어, 설정 변경, 소스 추가, 실패 복구 방법을 README에 작성.
- 테스트 서버에서 회의 설정 → 발표자 설정 → 알림 → 다음날 DM, 뉴스 발송, 문서 등록 → 질문을 검증.
- 실제 정기 스케줄은 최소 한 회차 운영하며 발송 누락·중복과 RAG 응답 시간을 확인.

완료 기준: FR-1~FR-12 수용 기준을 체크리스트로 점검하고, 배포 환경에서 재시작·데이터 복원·실패 로그 확인이 가능하다.

## 4. 공통 검증 원칙

- 일정 계산·선별·권한 규칙은 외부 API 없이 검증하고, 실제 연동은 별도 테스트 서버에서 확인한다.
- 일정 테스트는 시간을 주입해 수행하며, 실제 시간이 흐르기를 기다리는 방식에 의존하지 않는다.
- 네트워크 오류, 부분 전송 성공, 모델 지연, 권한 부족, 인덱싱 도중 종료를 재현한다.
- 발송 직후 저장 전 종료되면 발송 결과가 불명확할 수 있다. 실행 이력만으로 완전한 1회 전송을 보장한다고 가정하지 않고, 불명확 상태를 기록해 재발송 정책에 따라 처리한다.
- 범위 밖 채널의 문서가 검색 문맥과 답변에 포함되지 않는지 검증한다.

## 5. 구현 착수 시 필요한 운영 정보

- 테스트·운영 서버 ID, 공지·회의록 채널 ID, 팀장 ID, 관리자 역할 ID.
- 봇 토큰의 환경변수 등록과 필요한 Discord 권한 설정.
- 정기 회의 요일·시간, 승인된 뉴스 소스와 분반별 키워드.
- 임베딩·답변 모델 제공자, 이용 예산, 외부 모델에 회의록을 전달할 수 있는지 여부.
- 상시 실행할 배포 환경과 영속 데이터 저장 위치.

비밀값은 문서나 저장소에 기록하지 않는다. 운영 정보가 준비되기 전에도 샘플 데이터와 외부 연동 대역으로 공통 기반 및 업무 로직 개발은 진행할 수 있다.

## 6. 권장 릴리스 순서

1. **운영 자동화 MVP:** 단계 1~2 — 회의·발표자 관리와 모든 관련 알림.
2. **뉴스 포함 버전:** 단계 3 추가 — 매일 분반별 뉴스 발송.
3. **PRD 전체 버전:** 단계 4~5 추가 — 회의록 수집 및 출처 기반 질문·답변.

각 릴리스에 해당 범위의 단계 6 검증을 적용한다. 구현 착수 순서는 공통 기반 → 회의·발표자 → 뉴스 → RAG이며, 라이브러리 선정과 운영 정책 확정 후 세부 일정 추정을 한다.
